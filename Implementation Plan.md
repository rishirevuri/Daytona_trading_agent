SignalOps – Implementation Plan for a Reproducible Stock Market Prediction App
Introduction and Goals
SignalOps is a research-focused stock market prediction app designed for safety, transparency, and reproducibility. The system acts as a “Research Governor” agent that continuously proposes and evaluates trading signal improvements in a controlled environment, without ever giving real investment advice or placing live trades. All experiments are run as paper-trading simulations with full audit trails and strict guardrails to prevent overfitting or unsafe behavior. The primary goal is to maximize trust and reliability in algorithmic strategies by leveraging the hackathon sponsors’ technologies in a natural, integrated way:
Daytona – for executing backtests and data pipelines in isolated sandboxes, ensuring “same code, same data snapshot, same results” reproducibility with environment snapshots[1].
Sentry – for treating strategy performance drops or errors as first-class incidents, complete with trace spans and alerting (e.g. “Sharpe dropped 30% vs last week” triggers a warning issue).
CodeRabbit – for automated pull-request reviews focusing on domain-specific issues (data leakage, lookahead bias, missing fees/slippage, etc.) before any strategy changes are accepted.
ElevenLabs (optional) – for generating a brief audio “research briefing” after each experiment, enhancing presentation and accessibility.
By aligning with these technologies, SignalOps aims to excel in hackathon judging criteria: - Impact: Increasing trust in AI-driven trading research through transparency and rigorous validation. - Technical Execution: Deep integration of Daytona, Sentry, and others, demonstrating a robust end-to-end system. - Creativity: An autonomous agent loop that proposes experiments and even narrates findings, plus an optional “EarningsCall Lens” mode analyzing earnings call data. - Presentation: Clear dashboards, auditable reports, and audio summaries that make complex results easy to understand.
Scope: The app focuses strictly on paper trading and research. It will not execute real trades or provide personalized financial advice, ensuring compliance with financial regulations. All strategy outputs are considered hypothetical and come with prominent disclaimers of the limitations of simulation.
Key Constraints and Standards: We incorporate AI risk management and software security best practices at every step. For example, we follow NIST’s AI Risk Management Framework for identifying and mitigating AI-specific risks[2], and we apply OWASP’s Top 10 guidelines for LLM applications (e.g. guarding against prompt injection and insecure outputs)[3]. The system’s development practices align with the Secure Software Development Framework (NIST SP 800-218)【7†】 and supply-chain security frameworks (SLSA, reproducible builds), meaning every artifact and dependency is accounted for to ensure verifiability. By design, all code execution by the AI agent is constrained to safe sandboxes and approved tools, preventing unintended actions or external data exfiltration.
In summary, SignalOps will serve as a safety-forward, operator-verifiable research agent that maximizes the use of sponsor technologies (Daytona, Sentry, etc.) to deliver a credible and innovative stock market prediction research platform.

System Architecture Overview
High-Level Architecture: SignalOps is composed of modular components that work in concert to generate, test, and review trading signal strategies. The core workflow is an iterative loop where an AI agent proposes a strategy tweak or new experiment, runs it in an isolated environment, and produces an auditable report and code diffs. A web-based Developer Dashboard ties everything together, allowing users (or judges) to trigger experiments, monitor progress, and review results in real time. Below are the main components and how they interact:
LLM Research Agent: An AI agent (powered by an LLM like GPT-4 or Claude) orchestrates experiments. It decides on changes to the trading signal or model (e.g., adjusting a feature, trying a new dataset slice, tuning a parameter) based on past results and defined goals. Critically, the agent’s actions are limited to predefined tools (Daytona sandbox operations, Git operations, etc.) for safety. It communicates via the Model Context Protocol (MCP)[4], which provides a secure, standardized JSON-RPC interface for tool use.
Orchestrator Backend (API Server): A backend service (e.g., a FastAPI or Next.js API route) receives experiment requests (from the agent or a user action) and manages the lifecycle of each run. It interfaces with Daytona via its SDK or API to create sandboxes, execute code, attach data volumes, stream logs, and collect artifacts. The orchestrator also interfaces with Sentry for logging/tracing and with GitHub for creating Pull Requests (PRs).
Daytona Execution Sandbox: This is the core execution environment for backtests and data processing. Each experiment runs inside a fresh Daytona sandbox container – an isolated, reproducible environment that can be provisioned in seconds[5]. The sandbox is created with a specified base image (e.g., a Python 3.x environment with required libraries) and can have data volumes attached for large datasets or model weights. Within the sandbox, the orchestrator uses Daytona’s Git operations to check out the strategy code repository at a specific commit[6][7], ensuring the code is version-controlled. Then it uses process execution APIs to run the pipeline (data loading, feature engineering, model training, backtesting, etc.) step by step[6]. Daytona’s streaming log API is used to feed live logs back to the UI for real-time monitoring of the run[6]. After the run, important files (results, charts, reports) are fetched out of the sandbox via the file system API and stored persistently[6]. If the run is successful and produces credible results, we can snapshot the entire sandbox environment for later replay or audit[1]. In case an ML model needs training as part of the strategy, this can also be done inside the sandbox (leveraging GPUs if available) to capture the environment exactly; alternatively, the system can offload training to the developer’s local Mac (M3 Max, 36GB RAM) for efficiency, then save the model artifact back into the sandbox to continue the pipeline – ensuring the model and data are versioned for reproducibility.
Experiment Runner & Validator: This is the code (likely in a Python package, e.g. packages/core) that actually executes the strategy logic in the sandbox. It includes the backtesting engine, any ML model training code, and validation checks. The runner is invoked by the orchestrator (e.g., python run_experiment.py config.yaml). It reads a config/manifest (possibly generated by the agent) specifying the parameters and data for the experiment. The runner produces:
Calculated performance metrics (e.g., Sharpe ratio, drawdown) and validation statistics (like overfit indicators).
Structured outputs like metrics.json, returns.csv (time series of strategy returns), and any trained model files.
A research report (HTML/PDF) combining narrative (possibly partially AI-generated) with figures/tables.
A list of warnings or flags (e.g., “possible data leakage detected in feature X” or “overfitting risk high (PBO = 0.6)”).
These outputs are saved in the sandbox for retrieval.
Artifact Store & Database: All results from each run are saved for audit and comparison. A database (e.g., Postgres via Prisma in the Next.js app) keeps metadata on each experiment: timestamps, strategy name, commit SHA, data snapshot ID, metrics, etc. Large artifacts like reports or model binaries might be stored in cloud storage or as GitHub release assets. We also generate an SBOM (Software Bill of Materials) for each run’s environment (using SPDX or CycloneDX formats【11†】), which enumerates the exact package versions in the environment – this aids in supply-chain transparency and reproducibility checks.
GitHub Integration (PRs): The system treats any code or config change to improve a strategy as a pull request on the strategy’s repository. The AI agent, via the orchestrator, can create a new branch and open a PR through the GitHub API【54†】, attaching the experiment’s report and key results in the PR description. Each PR represents an experiment’s proposal (e.g., “Use 30-day rolling window instead of 20-day” or “Add sentiment data from earnings calls to features”). By using PRs, we naturally integrate with CodeRabbit for automated code review comments, and we ensure a human developer can easily inspect and merge changes after verification. Branch protections will be in place so that the agent cannot directly merge its own PRs – human approval is required as a final check.
CodeRabbit Review Bot: Once a PR is opened, CodeRabbit (installed as a GitHub App) will analyze the changes and provide feedback. We will configure CodeRabbit via a .coderabbit.yaml in the repo to focus on specific domain guardrails. For example, CodeRabbit will be instructed to:
Ensure no data from the future is accessed in the backtest (no lookahead bias).
Flag if a strategy is using information it couldn’t realistically have at the time (data leakage).
Verify that transaction costs (commissions, slippage) are accounted for in the simulation code.
Check that random processes (train/test splits, model seeds) are fixed or documented for determinism.
Check for proper documentation of changes (e.g., update to README or report).
CodeRabbit’s feedback appears as comments on the PR (e.g., “⚠️ The feature future_earnings might leak future data into the training window”). This provides an independent AI audit of the experiment’s code. The Developer Dashboard can pull these comments via GitHub’s API to highlight review findings in the UI.
Sentry Observability & Alerting: Every experiment run is instrumented with Sentry for performance tracing and alerting. The orchestrator will start a Sentry transaction for the run (e.g., transaction: "strategy_run"), and create nested spans for each phase of the pipeline (data loading, feature engineering, model training, backtest execution, report generation, etc.) to pinpoint where time is spent or where errors occur. We attach useful context to these spans/tags: strategy name, experiment ID, commit SHA, data version, Daytona sandbox ID, etc. This way, if something goes wrong (e.g., an experiment fails due to a code error or runs slower than expected), we have deep visibility. Additionally, the results of the run are reported as custom metrics to Sentry – for instance, we send the out-of-sample Sharpe ratio as oos_sharpe gauge, the max drawdown, the number of trades, etc., using Sentry’s metrics API[8]. We establish alert rules in Sentry to catch significant regressions: e.g., if oos_sharpe drops below a certain threshold compared to the last run or if an error flag is present, trigger an alert. These alerts can page the team (or for demo, simply highlight in the UI) that a strategy might have regressed or that the latest experiment is suspect. Sentry will also be used to capture incidents such as pipeline exceptions or assertion failures in validations – these become tracked issues that must be resolved.
Web-based Dashboard (Next.js): The user interface is a Next.js app (with Tailwind CSS for styling) that serves both a developer-friendly dashboard and a presentation layer for reports. Key UI elements include:
Strategy List Page: Shows all strategies or signals being tracked, with summary stats (last Sharpe, last run time, status indicators like healthy or needs review).
Experiment Detail Page: When an experiment is running or completed, this page shows a timeline of events. Thanks to Daytona’s log streaming, we can live-update the console output as the backtest runs[6]. We also show structured milestones (e.g., “Data loaded”, “Model trained – 85% accuracy in sample”, “Backtest completed – Sharpe 1.2” etc.). Once done, this page provides links to the generated report (viewable in-browser), the PR on GitHub, and any Sentry incident if triggered. If CodeRabbit flags issues, those can be displayed here too.
PR Review Center: A section of the UI where we aggregate CodeRabbit’s comments and possibly allow the user to give feedback to the agent or acknowledge the issues. This makes it easier to see all “concerns” about a proposed strategy at a glance.
Audit Trail & Snapshots: We provide views for compliance/verification, such as listing the Daytona audit logs[9] for a given run (every filesystem or process action inside the sandbox is logged), and the ability to re-run an experiment from a saved snapshot. The UI might have a “Reproduce” button that spins up a new sandbox from the saved snapshot ID and re-generates the results, proving determinism.
EarningsCall Lens (Alternative mode): If enabled, the UI lets the user switch to or initiate an “EarningsCall analysis” experiment (detailed later in its section). The UI/UX is similar, but the input is an earnings call transcript and the output focuses on NLP analysis and market reaction rather than trading strategy code changes.
Throughout the architecture, we maintain a principle of least privilege and maximum transparency. The AI agent is powerful in coordinating tasks, but each subsystem (Daytona, Sentry, GitHub, etc.) imposes boundaries that the agent cannot cross incorrectly. Daytona ensures code execution is isolated and can be easily inspected; Sentry ensures no error or anomaly goes unnoticed; GitHub/CodeRabbit ensures human oversight on code changes; and the UI ties it all together for the operator to verify each step.

Reproducible Experiment Execution with Daytona
At the heart of SignalOps is Daytona, which we leverage as a secure, reproducible “lab” for running all strategy experiments. Using Daytona’s sandboxing capabilities, we can guarantee that every experiment is executed in a clean environment that can be exactly recreated later – a huge boost for credibility in results.
Why Daytona: Daytona provides on-demand, isolated sandboxes that start in milliseconds[10], with support for various OS images (Linux, Windows, even macOS) and custom Docker/OCI images. For our Python-based backtesting pipelines, we’ll use a lightweight Linux image with Python and common data science libraries pre-installed (or define a Declarative Builder config to set up the environment with the exact dependencies we need[11]). Each sandbox is an ephemeral VM/container with root access for the code, but it’s completely isolated from other sandboxes and from the host, which means the AI agent can run potentially risky code (like new strategy logic) without jeopardizing the system’s security[12].
Lifecycle of a Sandbox Experiment:
Creation: When an experiment starts, the orchestrator calls Daytona to create a new sandbox (via SDK or MCP). We specify any needed parameters – for example, a name or an auto-stop timer so it shuts down after, say, 15 minutes if not used[13]. We also attach a volume to the sandbox that contains our dataset cache (historical market data, etc.)[14]. By using a persistent volume, multiple experiments can reuse downloaded data without each run hitting external APIs, while still keeping that data isolated within Daytona’s environment. If we have a previous environment snapshot (for instance, if this experiment is a rerun of a prior one or a continuation), we could instantiate the sandbox from that snapshot ID to load the identical state[15] – but for most new experiments, we start fresh.
Code and Data Setup: Inside the sandbox, the orchestrator will execute a series of setup steps:
Use Git operations provided by Daytona to clone the Git repository containing the strategy code into the sandbox[6]. We check out the specific commit or branch corresponding to the experiment (for a new agent-proposed change, it might be a temp branch the agent is working on). Daytona’s Git tool ensures no need for direct git command inside the sandbox with credentials – the Daytona API securely pulls the repo.
Ensure data availability: the sandbox can mount the volume where data lives. If the needed dataset version isn’t on the volume yet, the agent can trigger a download script (which would fetch data from an API or data source) within the sandbox. This data fetch can be restricted via Daytona’s network controls – we might allow the sandbox to call only specific data provider endpoints (by configuring network_allow_list on the sandbox)[16]. This prevents the agent from arbitrarily accessing the internet if not necessary.
Executing the Pipeline: With code and data in place, the orchestrator uses Daytona’s Process & Code Execution API to run the experiment. For example, it might run a command like python backtest.py --config configs/exp123.yaml. Daytona captures the output of this process. We utilize Log Streaming to get real-time logs[6]: as the code prints progress (e.g., “Loading data…”, “Training model…”, “Sharpe = 1.05”), those logs are sent to our backend and relayed to the UI’s timeline view. This real-time feedback is crucial for user trust during a long run – they can literally watch the strategy’s progress and see that nothing suspicious is happening (and terminate the run if needed).
Environment Isolation & Security: During execution, Daytona’s isolation means even if the strategy code tries something malicious or erroneous (like deleting files outside the working directory or making unauthorized network calls), it won’t affect anything outside the sandbox. We also make use of Daytona’s audit logging feature – every filesystem write, process execution, or network request can be recorded[9]. These audit logs are invaluable for later analysis (we can answer: what exactly did this code do? Did it access only allowed resources?). In an operator view, we might expose these logs to prove nothing unsafe occurred.
Result Collection: After the process finishes, the orchestrator inspects the exit code and output. If it’s a success (exit code 0), we proceed to gather artifacts. Using Daytona’s File System tools, we copy out key files: the manifest.json (inputs and versions), metrics.json, any charts or data files, and the compiled report.html/report.pdf. These are saved to our artifact store or attached to the PR. If the process failed (non-zero exit or exception), we still gather the logs and perhaps the partial outputs for debugging. In both cases, the sandbox can then be stopped to free resources (Daytona can auto-stop after a period of inactivity as well).
Snapshot (for Reproducibility): One of Daytona’s killer features is Environment Snapshots – capturing the entire sandbox state so it can be resumed exactly later[1]. We will take a snapshot at the end of each successful run. This snapshot includes the environment with all installed packages, the exact code as run, and any intermediate state. With a snapshot, we or the judges could later say “prove this result is reproducible” – our system can spin up a new sandbox from that snapshot and re-run the final report generation, expecting identical outputs. Snapshots also allow us to “fork” experiments: e.g., if strategy A did well, fork its snapshot to tweak a parameter and see if result holds, without starting from scratch. Daytona’s snapshot mechanism is programmatic (via SDK, no manual steps)[17], so the agent can invoke it automatically. We will need to monitor snapshot storage usage (since many snapshots could consume space), but for the hackathon scale this is manageable.
Cleanup: Daytona sandboxes are ephemeral; once results are secured and possibly snapshot taken, we terminate the sandbox. This ensures no leftover processes or costs. (In a future enhancement, we might keep a few sandboxes running for interactive debugging via the VS Code or SSH features[18] if a human wants to jump in – but by default the agent’s runs are headless.)
Best Use of Daytona – Showcase Features: To maximize our Daytona integration (a likely judging point), we emphasize: - “Replay Run”: From the UI, a user can select any past experiment and click “Reproduce in Daytona”. Under the hood, this fetches that run’s snapshot ID and starts a sandbox from it, then executes the saved manifest’s steps. If everything is truly reproducible, the resulting metrics should match and the UI can highlight that. This demonstrates deterministic reproducibility in front of the judges. - Environment Fingerprint: We display the identifiers (or checksums) of the sandbox image and snapshot used for each run. For example, “Base Image: daytonaio/python:3.10-slim@sha256:abc123, Snapshot ID: #snap-20260101-abc123”. This assures everyone that the environment was consistent. Daytona’s use of container images means we can pin to exact digests【30†】. - Volume for Data: We mention in the UI or docs that “Large data is handled via Daytona Volumes to avoid bulky data in Git and allow caching between runs” – an efficient and practical use of Daytona[16]. - Audit Trail Integration: For a given experiment, the UI can link to “Audit Log” which is a filtered view of Daytona’s audit events for that sandbox (possibly fetched via Daytona’s API or webhook on sandbox actions). This level of transparency (showing every file read, every process run in the sandbox) underscores our commitment to safety and verifiability[9].
By harnessing Daytona in this manner, we ensure that every experiment is isolated, repeatable, and observable – addressing one of the biggest challenges in algorithmic trading research: the ability to trust that results aren’t due to some hidden environment quirk or data mismatch. Daytona essentially gives us trust through environment transparency and control[19][20].

Observability and Incident Tracking with Sentry
SignalOps treats the performance of trading strategies similar to how one would treat the performance of a production system: any degradation or anomaly is a potential incident to be investigated. We integrate Sentry deeply to monitor each experimental run and flag issues, which both improves the development process and serves as a safety mechanism if the agent’s proposals lead to worse outcomes.
Performance Tracing: Each experiment run is instrumented as a Sentry transaction (e.g., named "StrategyRun: {strategy_name}#{run_id}"). As the orchestrator kicks off different phases in the pipeline, it will start and finish Sentry spans to record the duration and outcome of each phase. For example: - span "data.load" – when loading historical data. - span "features.generate" – when computing technical indicators or features. - span "model.train" – if an ML model is being trained on in-sample data. - span "backtest.run" – the core loop simulating trades on historical data. - span "metrics.compute" – computing summary statistics. - span "report.generate" – compiling the final report.
Each span can include annotations (tags) like dataset ID, number of records processed, model hyperparameters, etc., where appropriate. If an error occurs in any step (exception thrown), the span will record that and Sentry will flag the transaction as errored. This fine-grained tracing serves several purposes: - We can easily identify performance bottlenecks (e.g., data loading took 10 minutes due to huge CSV parse – maybe we need to optimize that). - If a run fails, the trace shows exactly which step failed and with what error, aiding debugging. - We build confidence that even as experiments change, the overall runtime is under control and within expected bounds (important in a live demo setting).
Metrics & Alerts: Beyond timing information, we leverage Sentry’s Custom Metrics feature to log domain-specific results for each run. The experiment runner (in the sandbox) or the orchestrator can send metrics like: - Sharpe ratios – sharpe_is (in-sample Sharpe) and sharpe_oos (out-of-sample Sharpe). - Max Drawdown – max_drawdown. - Profitability – e.g. win_rate (percent of trades that were profitable). - Trade count or turnover – trade_count, portfolio_turnover. - Overfit risk metrics – such as pbo (Probability of Backtest Overfitting) value, or a boolean overfit_flag. - Any constraint violations – e.g. leakage_detected = 1 if our validations found potential leakage.
These metrics are tagged by strategy and run, so over time we accumulate a time series of each metric per strategy. Sentry’s Alerts can then be configured, for instance: - If sharpe_oos drops by more than 20% compared to the previous run for the same strategy, trigger an alert (regression detected). - If overfit_flag = 1 or pbo > 0.5 on a run, open an issue or send a notification that the experiment likely overfit. - If any run results in an exception (Sentry error event), notify the team immediately.
During the hackathon demo, this could be showcased by intentionally introducing a bad change and showing Sentry catching it (e.g., the agent tries something that causes Sharpe to plummet; Sentry alert pops up highlighting the drop).
We treat these alerts as incidents – in a real deployment, the team would triage them. For hackathon purposes, they demonstrate our commitment to stability: the system not only searches for better strategies, it also actively watches for and flags deteriorations.
Issue Tracking & Attachments: In cases of failures or significant incidents, we enrich Sentry error events with attachments for easier debugging[21]. For example, if a backtest failed due to an assertion in validation (say we asserted no lookahead and it triggered), we can attach: - The manifest.json of that run (so the exact parameters are known)【37†】. - A snippet of the log around the error. - Perhaps the diff of code changes the agent made for that run (so we see what it tried to change).
This makes Sentry a one-stop hub for investigating “what went wrong” in any given experiment.
Release Tracking: We integrate Sentry’s release feature by tagging events with the Git commit SHA of the strategy code. This way, if an issue arises, we know exactly which code version it came from【35†】. We can mark new strategy versions (especially if we merge a PR) as a Sentry release, and monitor if the next scheduled run after that release shows any new issues. This parallels how one would track software releases – here we track strategy iterations.
Cron Monitoring: If we schedule periodic re-runs of strategies (say nightly evaluation of current strategies on latest data as a “shadow deployment”), we can use Sentry’s Cron Monitoring to ensure these jobs run on schedule【33†】. Each scheduled run sends a heartbeat to Sentry; if one doesn’t happen, that might indicate the agent failed to schedule or the orchestrator is down, which would be flagged.
In summary, Sentry provides a safety net and a rich telemetry backbone for SignalOps. By logging not just traditional errors but also financial performance metrics, we treat the strategies’ behavior as the monitored “application”. This approach is novel in the finance context – it’s like treating a drop in Sharpe ratio akin to an increase in error rate in a web service, something needing immediate attention. This will stand out to judges as a creative “treat quant research like DevOps” mindset. It leverages Sentry beyond basic error logging, showing a “best use of Sentry” through custom domain metrics, performance tracing, and automated incident creation.

Pull Request Workflow and Code Review with CodeRabbit
To ensure all strategy modifications are thoroughly vetted, SignalOps uses a Pull Request (PR) based workflow for any code or configuration change. This not only keeps a history of changes but also enables integration with CodeRabbit – an AI code reviewer specialized in catching issues in PRs.
PR-Driven Experiment Cycle: When the AI research agent formulates a new experiment, any change to the strategy’s code (or YAML config) is made on a new Git branch (e.g., agent/exp42-new-feature) in the repository. Instead of pushing directly to main, the agent (via the GitHub API) opens a PR comparing that branch against the main branch【54†】. The PR description is populated with the context of the experiment: - A high-level summary of what the experiment is (“This PR tests adding a 30-day moving average signal to the strategy”). - The manifest of the run (as a JSON/YAML block, showing parameters, dataset version, etc.). - Key results (perhaps a table of old vs new metrics, e.g., “Sharpe from 1.0 to 1.1, max drawdown from 15% to 12%”). - Any warnings or flags raised (like “Note: PBO estimate is high; results might be overfit.”). - A link to view the full HTML report artifact (which includes charts and detailed analysis).
By structuring it this way, a human reviewer (or judge) can quickly grasp what the agent did and why, and see evidence before digging into code.
CodeRabbit Automated Review: Once the PR is opened, CodeRabbit (which we’ll have installed in the GitHub repo beforehand) will automatically start its AI review of the changes. We leverage this by customizing CodeRabbit’s configuration to focus on the nuances of quantitative code. In the .coderabbit.yaml config, we will include review instructions that highlight these points: - Data Leakage & Lookahead: “If any code change introduces using future data (e.g., using df.shift(-1) on prices to compute a label within the training period), point it out.” We expect CodeRabbit to catch things like labels or features that depend on future knowledge. - Proper Train/Test Separation: Ensure that if the strategy is doing any ML training, the training data is separated from test (no contamination). CodeRabbit can detect if a test dataset seems to include training range, etc., especially if we label our code clearly. - Fees & Slippage: Check that any backtest transactions account for fees (commission) and slippage. For example, if the code has an order execution model, it should subtract a fee or adjust price for slippage. If the PR removes or forgets fees, CodeRabbit should comment that “trading costs seem to be missing or set to zero – this might inflate performance.” - Reproducibility & Determinism: Flag if any introduction of randomness lacks a fixed seed. If the code uses random or np.random without seeding in the backtest or model training, that’s a reproducibility issue. - Documentation and Clarity: Ensure that the PR includes updates to documentation as needed. For instance, if a new parameter is added, is it described somewhere? If a new dependency is added, is requirements.txt updated? These are more general but still important. - Security/Safety in Code: Though the sandbox limits a lot, if the code, say, tries to open a network connection or write to an odd path, CodeRabbit might flag it. We can instruct it to ensure the code doesn’t have unexpected side-effects (beyond the allowed scope).
Because CodeRabbit uses AI models to analyze code, it can understand the context somewhat. For example, it might recognize a pattern known to be problematic in finance (like using forward-filled data for future times). Our config will aim to surface such domain knowledge.
Workflow Integration: The Developer Dashboard will show a status for the PR review. We might have an indicator like “CodeRabbit Review: 2 issues found”. The user can click to see details, which are essentially the comments CodeRabbit made. For the agent, we could even feed a summary of CodeRabbit’s feedback back into the agent’s prompt so it can iterate (e.g., if CodeRabbit says “You forgot to include fees,” the agent might decide to fix that in a subsequent commit). However, we must be careful: CodeRabbit’s comments, while generally helpful, are external AI-generated content – we don’t want to blindly trust it in an automated loop (risk of prompt injection or incorrect advice). So likely, we’ll use CodeRabbit feedback as advisory, requiring either human confirmation or very strict parsing before the agent acts on it.
No Self-Merging: The CI will be configured so that a PR needs at least one manual approval and passing checks (tests, lint, CodeRabbit, etc.) before merge. This means the agent cannot accidentally merge a change that hasn’t been reviewed. If the agent wants to persist a change, it might need an override from an operator (which is a safety check in itself).
Security Considerations for PR Flow: We treat CodeRabbit and GitHub as part of the attack surface. To mitigate risks: - The GitHub credentials the agent uses (likely a fine-scoped token) can only push branches and create PRs, not directly push to protected branches. - CodeRabbit’s app is given least required permissions. It will not be allowed to auto-merge or make code changes, only comments. - We’ll be mindful that PR titles or descriptions could be a channel for prompt injection into CodeRabbit (since CodeRabbit reads them). However, since our agent controls those fields and we trust our agent’s prompt, this risk is minimal. Still, we avoid including any untrusted user input in the PR content.
By using the PR & CodeRabbit approach, we turn every experiment into an auditable code review event. For the hackathon demo, this means we can show judges a PR diff of what the agent changed (“see, it only changed these 2 lines to increase the moving average window”) along with CodeRabbit’s commentary (“CodeRabbit confirms no obvious data leaks and that the changes are consistent with best practices”). This level of scrutiny is rarely seen in AI agents and will underline the safety and professionalism of our project.

Audio “Research Briefings” with ElevenLabs (Optional)
To elevate the presentation of results, SignalOps can generate an audio briefing for each experiment using the ElevenLabs text-to-speech (TTS) API. This feature is primarily to impress during demonstrations – it provides a succinct spoken summary of the experiment’s outcome and key findings, making the platform feel like a personalized analyst giving a briefing.
Purpose and Content of Briefings: After an experiment concludes and the report is generated, the system composes a 30-60 second summary, which might include: - What was tried: e.g., “We tested adding a sentiment signal from earnings call transcripts to the momentum strategy.” - Key results: “The new strategy’s out-of-sample Sharpe ratio improved from 1.0 to 1.15, and maximum drawdown reduced by 5 percentage points.” - Significance: “This suggests the sentiment signal may be capturing information the price-based signals missed. However, the deflated Sharpe Ratio is below 0.5, indicating the result might be a false positive[22].” - Risks and next steps: “We observed increased turnover which could incur higher trading costs. The next experiment might refine position sizing to manage this.”
This text is generated by the agent or a template filled in with actual metrics. We then use ElevenLabs API to convert it to speech.
Integration with ElevenLabs API: ElevenLabs offers a developer-friendly API for TTS. We will likely use the Python SDK or direct REST calls. The plan is as follows: - Choose a voice (ElevenLabs provides a variety of realistic voices, possibly even allowing a custom voice clone if desired). For our purposes, a clear, professional voice (male or female) with good enunciation for technical terms is ideal. - Use the low-latency model since we want quick turnaround. ElevenLabs has an “eleven_monolingual_v2” or similar model that balances quality and speed. - The API can stream audio as it’s generated[8], which is great if we want to play it immediately. Backtesting Pipeline and Overfitting Guardrails
The core of SignalOps from a quantitative perspective is the backtesting and validation pipeline. This is where we simulate the strategy on historical data and evaluate its performance. The twist is that we embed numerous guardrails and statistical checks to ensure that a “good” backtest isn’t just an overfit illusion. Below are key design points of the pipeline implementation:
Backtesting Engine: We need a reliable, fast backtesting library. Options considered include vectorbt, backtrader, Zipline, etc. For an MVP, vectorbt is attractive since it’s vectorized and can run many strategy simulations quickly (great for rapid experimentation)【34†】. It easily handles technical indicator calculations and portfolio returns in a vectorized way using NumPy/Pandas, which is well-suited for research loops. On the other hand, backtrader is a classic engine that has built-in support for things like different broker commission models and slippage【43†】. We could even mix approaches: use vectorbt for quick stat calculations and backtrader for a “ground truth” simulation if needed. Given our focus on Daytona (which can scale compute) and reproducibility, we may start with vectorbt for simplicity, and ensure that it’s configured for determinism (no random fills, etc., unless we explicitly want randomness).
Fees and Slippage: Every backtest run will include transaction cost modeling by default. We will not let the agent or user run a backtest without these realism factors, to avoid painting an overly-rosy picture. For example: - Commission fee: assume a per-trade fee or a percentage of trade value (depending on asset class). This can be a fixed number (like $0.001 per share or 0.01% per trade) or pulled from realistic brokerage fee schedules. Backtrader and Zipline both allow setting commission models easily【43†】. - Slippage: We’ll implement at least a simple slippage model (e.g., slippage = 0.1% of trade value or based on daily volume). Backtrader allows slippage settings (like ‘volume share’ slippage)【43†】; in vectorbt, we might have to manually adjust fill prices. - These parameters are part of the experiment manifest so that they are transparent and can be tweaked. We might run sensitivity analysis as part of validation: “if slippage was double, does strategy still profit?” – if not, that’s a red flag that the edge is narrow.
Walk-Forward Out-of-Sample Testing: To avoid overfitting on one period, our pipeline uses a walk-forward approach. That is, we divide the data into chronological segments: e.g., train on 2015-2018, test on 2019; then train on 2015-2019, test on 2020; etc. This provides multiple out-of-sample evaluations. We’ll get metrics for each window. Ideally, the strategy performs consistently, not just in one lucky period. The agent’s proposals should be evaluated on out-of-sample metrics first and foremost (e.g., it shouldn’t optimize purely on in-sample score).
We also consider techniques like Combinatorially Purged Cross Validation (CPCV) from López de Prado’s work, which helps estimate the probability of backtest overfitting. Implementing full CPCV might be complex, but we can likely utilize the concept of PBO (Probability of Backtest Overfitting)[23]. PBO essentially asks: if you have many alternative strategies, what is the chance the best one in-sample will do poorly out-of-sample? We can simulate variations of the strategy (perhaps the agent in trying many experiments inherently does this) and then calculate PBO by comparing ranks of performance IS vs OOS[24]. A high PBO (close to 1) would mean our strategy is probably overfit (finding patterns in noise). The pipeline will calculate a PBO estimate when possible and include it in the report.
Deflated Sharpe Ratio: We incorporate the Deflated Sharpe Ratio (DSR) methodology[22] to adjust the Sharpe ratio for the number of trials and other biases. The DSR gives a more realistic assessment of whether a given Sharpe is statistically significant or could be due to chance (multiple testing bias). For example, a raw Sharpe of 2 might sound great, but if the agent effectively tried 100 parameter combos to get that, the DSR might tell us that it’s not actually significant. We will compute DSR using the formula from López de Prado’s paper (or use an existing implementation if available) and present it alongside Sharpe. If the DSR is below a threshold (e.g., corresponding to <95% confidence), we flag the result with a warning like “Deflated Sharpe suggests this result might be a false positive due to multiple testing[22].”
Stability and Robustness Checks: Beyond just train/test splits: - Subperiod Performance: The pipeline will automatically evaluate performance in different market regimes (bull, bear, volatile, calm). For example, how did the strategy do in 2020 vs 2021 vs 2022? If a strategy only works in a trending market and crashes in a sideways market, we want to know that. We can generate a table or chart of year-by-year (or quarter-by-quarter) returns. - Parameter Sensitivity: If the strategy has key parameters (lookback window, threshold, etc.), we can do a grid test around the chosen value. If small changes in parameters result in vastly different performance, the strategy might be over-tuned. The agent, when proposing a strategy, could request a quick parameter sweep which the pipeline can run (in a vectorized manner perhaps) and produce a heatmap of performance. If our chosen parameter isn’t in a stable zone of that heatmap, it’s concerning. - Simulated Realism Variations: We can vary slippage and fees to see if the strategy remains profitable under slightly worse conditions. This essentially tells us the strategy’s margin of error.
Data Leakage Tests: We incorporate explicit tests to ensure no lookahead: - The code will include assertions or checks that training data end dates precede test start dates, features that are supposed to use past data truly use only past data. For instance, if a feature is the last 10-day average of volume, we ensure it’s computed with a rolling window that does not peek into the future by off-by-one errors. - If the agent adds a new feature, perhaps a rolling statistic, it must be careful to shift appropriately. We can detect if a feature value correlates too perfectly with future returns (a giveaway of leakage) by simple statistical tests. - We also ensure that any sort of universe selection (like picking which stocks to trade) doesn’t inadvertently use future info (a common survivorship bias issue). If using stock data, we’d use point-in-time universe definitions.
If any leakage or suspicious behavior is detected, the pipeline can throw an error or warning, which either stops the run or marks it as invalid. This ties into Sentry (incident reporting) and CodeRabbit (which might catch it too at code review time). Essentially, two layers: one at code review, one at runtime validation.
Paper Trading vs Backtest Acknowledgment: While backtesting tries to simulate reality, we will prominently remind users of the limits of backtests and even paper trading. As highlighted by Alpaca’s documentation, paper trading doesn’t capture certain real-world market effects[25]: - It doesn’t simulate market impact – in real trading, our orders could move the price if they’re large. - It doesn’t account for order queue position – paper trading might assume you get filled at the market price, but in reality your limit order might not fill. - No simulation of halts, extreme events handling, or regulatory fees beyond basic ones. - It assumes perfect data availability with no latency.
We list these in the report’s disclaimer section to ensure no one interprets a good backtest as a guaranteed real performance[25]. We want to show judges we are fully aware of these nuances.
In conclusion, our backtesting pipeline is not a naive “take data and compute PnL” – it’s a research-grade evaluation harness. By integrating overfitting detection (PBO, DSR) and by actively looking for pitfalls like leakage and hidden bias, we differentiate SignalOps as a platform that doesn’t just chase performance blindly, but critically assesses it. This rigorous approach will likely resonate with any judges with finance knowledge, and for those without, our clear flags and warnings in reports will make it evident that we are catching “too good to be true” situations. It’s a concrete demonstration of AI safety in an algorithmic trading context – preventing the agent from convincing us to deploy a strategy that only looked good due to backtest overfitting.

Data Ingestion, Versioning, and Reproducibility
Accurate and reproducible experiments depend on consistent data. SignalOps will enforce strict data versioning and provenance tracking for all datasets used in backtesting and modeling.
Market Data Sources: For stock price data, there are a few options: - If using Alpaca’s API, as an Alpaca user we have access to free real-time and historical data (IEX for US stocks)[26]. We could use Alpaca’s data for convenience and public availability. Alternatively, free sources like Yahoo Finance or Alpha Vantage (with rate limits) could be used for daily data. Since the user prefers minimal paid APIs, we lean towards free data. - For alternative data like earnings call transcripts (used in the “EarningsCall Lens” feature), sources include publicly available transcripts via company investor relations or third-party APIs. Many APIs (like Finnhub, Polygon, etc.) require at least a free tier API key. We will use a source that allows caching the transcripts for research (some are available on EDGAR for prepared remarks, but Q&A might not be, so likely use a service with permissible use).
Data Fetching and Caching: We decouple data ingestion from the backtest. Data ingestion scripts (which can also run inside Daytona sandboxes or locally) will fetch raw data and store it in a structured format (e.g., CSVs or Parquet files). We then version these data files: - Each dataset (e.g., “daily_prices_SP500_2010-2023” or “AAPL_earnings_calls_2015-2023”) has a version ID or timestamp. If data is updated (say new days added or corrections made), that constitutes a new version. - We can integrate with Data Version Control (DVC) or a simpler approach like storing data files with a hash in the filename. DVC would allow us to manage large files via git pointers and even connect to cloud storage【48†】. For hackathon simplicity, we might not fully integrate DVC, but we will follow its principles: never modify a dataset in-place without changing its version identifier, and keep track of which version was used for each run. - The experiment manifest includes references to dataset versions used. For example: "data_version": "prices_v20260101".
Reproducibility of Data Transformations: Often, the raw data needs preprocessing (corporate actions adjustments, etc.). We ensure those transformations are either: - Deterministic and coded (and versioned) in our pipeline (e.g., we apply a fixed procedure to split-adjust prices, which doesn’t change unless code changes). - Or if using an external library or API for it, we capture the output as a static dataset for that version.
Rolling Window Features: Many signals rely on rolling statistics (moving averages, RSI, etc.). We will use Pandas’ rolling functions with an explicit min_periods and careful alignment to avoid forward-looking bias【49†】. For example, computing a 20-day moving average at day T will only use days < T in the calculation. We double-check alignment off-by-one issues diligently.
Storing Intermediate Data: If an experiment involves training an ML model (say a regression or a neural network on historical features), the trained model (weights) is also an artifact. We might not keep every model (since they can be large), but we at least store a hash or signature of it, and important metadata like training data period, features used, hyperparams. This ensures if the agent says “I trained a LightGBM model and here are its backtest results,” we know exactly what that model was. In a reproducible run, we could retrain it (since we have the code and data snapshot), but to save time we might load the saved model to skip retraining – however, that is only okay if we guarantee determinism (fix random seed in training, etc.).
Daytona Volume for Data: As mentioned, we attach a persistent volume in Daytona to hold datasets. Prior to the first run, we can pre-seed this volume with required data (by running a sandbox that downloads everything). Then, for each experiment sandbox, we attach the volume read-only or read-write as needed. This way, experiments don’t have to download the same historical data each time (saving time and API calls), and we ensure consistency (they’re literally using the same files). The volume’s content can be considered the “ground truth” dataset collection.
Licensing and Compliance: We will respect data source licenses – for example, if using IEX data from Alpaca, we note that it’s for simulation and not redistributed. Earnings call transcripts can be copyrighted by the provider; if needed, we restrict usage to just analysis and do not display full transcripts to end users (only our derived sentiment scores, etc.). We might include in our documentation that any third-party data remains property of its owners and is used under fair use for research, etc., to cover ourselves legally.
Example Data Workflow for an Experiment: 1. The agent decides to use a new dataset, say “social media sentiment”. The orchestrator finds we don’t have it locally. 2. We spin up a sandbox with internet access allowed for the specific API (maybe a separate ingestion sandbox) and run the fetch script (with an API key stored securely). 3. The data is saved to the volume and given a version tag (perhaps the date of retrieval). 4. Subsequent experiments now use that cached data, and refer to it by version. 5. If the data is time-series that updates (like new daily prices), we treat new data as a new version (e.g., prices_v20260201 for an update in Feb 2026). The agent or user can trigger data update as a deliberate action.
By handling data like code (version-controlled, immutable once versioned), we eliminate a major source of irreproducibility in finance experiments. Judges will appreciate that our runs can be rerun in 6 months and still use the same data version to get the same results, rather than drifting as data updates. This is often overlooked in hackathon projects; highlighting it will show our thoroughness.

Reporting, Audit Artifacts, and Run Reproducibility
Every experiment in SignalOps produces a comprehensive set of artifacts that document what was done and what was found. These artifacts are crucial for auditability, collaboration (e.g., code review on PRs), and reproducibility. Let’s outline what we generate and how we use it:

This manifest is included in the report and stored alongside outputs. It’s essentially the recipe for the experiment, which is invaluable for reproducibility. If someone has this manifest and the code, they should be able to rerun the experiment exactly (especially since we also have the environment snapshot).
Metrics and Results Summary: A machine-readable metrics.json is produced, containing key performance metrics: - For each out-of-sample period: Sharpe, CAGR, volatility, max drawdown, Calmar ratio, Sortino ratio, etc. - Overall aggregated metrics (maybe across full test period or average of folds). - Overfit statistics: PBO, DSR, number of trials (if applicable). - Constraint metrics: e.g., average turnover, average holding period, any risk metric (like beta to S&P500 if relevant). - These metrics allow quick comparison between runs and can be ingested into a database for generating leaderboards or tracking progress over time.
Trade Logs: If applicable, we output trades.csv or similar, listing each simulated trade (timestamp, asset, quantity, price, type, fees applied, etc.). This is useful for deep dives (e.g., looking at any particular trade that might be unrealistic).
Returns Time Series: A returns.csv (or equity curve CSV) is output so we can plot the equity curve or do statistical analysis on the returns outside the system if needed. This file typically has columns like date, strategy_return, maybe benchmark_return.
Human-Readable Report: We plan to use a tool like Quarto or Jupyter Notebook to generate an HTML/PDF report【52†】. The report serves as a self-contained analysis: - Title and Metadata: including strategy name, date, who/what ran it (the agent), and links to code and data versions. - Overview: a plain-language summary of what the strategy is and what this experiment changed (could be auto-written by agent in markdown). - Performance Summary: key metrics in a table. - Charts: e.g., equity curve chart, drawdown chart, bar chart of yearly returns, maybe a rolling Sharpe graph. - Validation Results: could include a heatmap of parameter sensitivity, a graph showing distribution of IS vs OOS performance across folds to illustrate overfit, etc. - Diagnostics: any warning is clearly explained here. We aim for the report to be polished enough for a portfolio or management to read, but also contain enough detail for a quant to audit. Quarto can combine narrative text (which we can supply with the help of the agent) and code outputs seamlessly, which is ideal.
Artifacts in CI and PR: All these artifact files can be attached to the GitHub PR as well, using GitHub Actions to upload them as build artifacts【53†】 or using the PR comments (perhaps post a comment like “View the report [here] and download metrics [here]”). This ensures that even outside our UI, anyone reviewing the PR can access the outputs.

This is done perhaps via a tool (there are Python or Node tools to generate SBOMs from lockfiles or environments). This SBOM lists all packages and versions in use (and could be attached to the PR or stored with the run). The reason is to show supply chain transparency – we know exactly what libraries (and versions) were used to produce a result. If later a bug is found in a library, we can trace which experiments might be affected. This might be overkill for a hackathon, but even a simple requirement.txt freeze is a step towards that. Still, including mention of SBOM demonstrates our forward-thinking on reproducibility and security.
We can also consider generating a SARIF report from a static analysis or security scan of the code (maybe run Bandit or similar on the code, or even check for vulnerabilities in dependencies). This can integrate with GitHub code scanning【55†】. Again, not typical in quant projects, but it’s something we can showcase to indicate we thought of security (e.g., “no hardcoded secrets, no obvious SQL injection” – the latter not so relevant here).
Audit Logs: We will store Daytona’s audit logs for runs in our database or at least have them accessible. If needed, one can inspect them to see every command and file access. For instance, in an appendix or separate artifact, we could include “Daytona_audit.txt” which lists the sandbox operations performed (the platform may provide these via API). User & Judge Experience: When a judge looks at our app during the demo, they can: - Click on a past experiment, see the summary on screen and, if interested, click “Download Full Report (PDF)” to get the nicely formatted document to peruse. - They might also see a “Reproduce” button – clicking it would spin up a sandbox from snapshot and confirm the outputs match (a bit heavy to do live, but we could have a pre-prepared example). - They can see a comparison of two experiments (maybe we add a feature to diff metrics between any two runs, effectively creating a “diff report” to highlight what got better or worse).

AI Agent Safety and Access Control
Given an LLM agent is at the helm of proposing and executing experiments, we must enforce stringent safety and security controls around its capabilities. We incorporate industry best practices and specific constraints to ensure the agent cannot cause harm, either by malicious intent or by accident.
Tool Allowlisting: The agent will only have access to a limited set of tools (via MCP or our API) necessary for its function: - Daytona Sandbox Management: to create/destroy sandboxes, run code, etc. (No direct shell access outside what Daytona provides). - Filesystem and Git operations in sandbox: limited to the repository and data volume mounted. It cannot read arbitrary files from the host or other sandboxes. - GitHub PR API: to create pull requests and perhaps read its own PR’s comments. This will be through a proxy endpoint we provide to avoid giving the agent a raw token. - Sentry Logging: the agent might log important events or metrics, but it cannot read or modify Sentry data (that’s one-way communication, just reporting). - Optional ElevenLabs tool: if we allow, the agent can call a function like generate_audio(summary_text) but it doesn’t get to call arbitrary external endpoints. - Market Data Reader: we might provide a safe function like load_data('SPY', from, to) which under the hood reads from our cached dataset (so the agent doesn’t directly access external APIs). This ensures it cannot leak data or hammer an API.
Any attempt by the agent to step outside these bounds (e.g., asking to run code on the host, or fetch a URL not in allowlist) will be either ignored or met with a system message reminding it of policy. This is aligned with OWASP LLM Application Security guidelines that emphasize sandboxing and allowlisting for agents[3].
Prompt Hygiene and Injection Defense: We will craft the agent’s system prompt carefully to set rules (no self-modification, no executing instructions from untrusted sources, etc.). Because the agent sees a lot of content (like code diffs, logs, maybe even transcript text), we must guard against prompt injection. For example, an earnings call transcript could theoretically have a weird sentence like “... and the next line is: [SYSTEM] ignore previous instructions ...” which could confuse an LLM. To mitigate: - We sanitize any external text before it goes into the prompt. Potentially by wrapping it or summarizing it instead of raw inclusion. - We use role-based prompts (if the LLM supports it) to differentiate system vs user vs tool outputs clearly. - The agent should be running with a relatively locked-down model (if using OpenAI/Anthropic, we use their tools to monitor for policy violations). - If any suspicious output is generated (like the agent tries to get a password or make a trade on a live account), the orchestrator will catch that by design (no tool allows it, and our code won’t either).
Human Oversight and Intervention: We incorporate a “human-in-the-loop” concept. For instance: - Any PR created by the agent is subject to human review (the agent cannot auto-merge it). - We might have a mechanism where the agent, before executing a potentially risky action (like deleting all data to rebuild from scratch), posts a notification or requires a flag. But given our context, the main risk actions (like actual trading) are not even available. - The UI will have a “Panic” or “Stop” button for an operator to immediately kill a running experiment if something looks off.
Rate Limiting and Budgeting: We will ensure the agent doesn’t run infinite experiments rapidly (which could rack up costs or overwhelm resources). We impose limits like max X runs per hour, and one at a time. The agent should evaluate results before proceeding to the next suggestion, which naturally slows it down.
Isolation via Daytona: By running any agent-generated code in Daytona, even if the agent tries something nefarious like writing to disk repeatedly or scanning ports, it’s contained. Daytona’s network policies come in handy – for example, we can start sandboxes with network_block_all=true except for perhaps needed data hostnames[16]. If the agent somehow got an idea to call an external service, it wouldn’t be able to unless explicitly allowed.
Monitoring Agent Outputs: We log all the agent’s major decisions and rationale (the chain-of-thought can be captured if we use something like Azure OpenAI with logging, or we manually log the prompts and responses). This is for post-mortem analysis if it does something odd. It’s also an audit trail proving we didn’t give it any hidden harmful instruction.
MITRE ATLAS Consideration: MITRE’s ATLAS is a threat matrix for adversarial AI usage[27]. Some relevant threats include: - Prompt injection (addressed above). - Data poisoning – e.g., if the training data or test data is maliciously manipulated to trick the agent. We mitigate by using trusted data sources and version control (if data changed unexpectedly, we’d notice a new hash/version). - Model denial of service – e.g., feeding the agent input that is huge or complex to make it waste time or fail. We control the size of inputs (like limit how large an earnings transcript we feed at once, perhaps summarizing first). - Supply chain attacks – our CI and dependency pinning help ensure the code environment is what we expect (no typosquatted packages, etc., as we review any new dependency the agent introduces).
Recent MCP Security Note: We are aware of recent news that even official MCP servers had vulnerabilities when combining tools【56†】. This means we should be cautious in how we configure the MCP and any tool manifests. We will: - Host the MCP server ourselves (likely via the Daytona CLI daytona mcp start in a secure way) and not expose it beyond local or required scope. - Make sure any tool plugin for MCP (like a custom tool to call our backend) is simple and reviewed. We won’t, for example, plug in a shell tool that could be abused. - Keep the MCP server updated (Anthropic donated it to Linux Foundation, implying it’s open and community-driven, meaning we should keep an eye on updates).
No Live Trading or Personal Advice: We reiterate: the agent is explicitly instructed that it cannot and should not attempt to engage in live trading or give recommendations to users. Its role is researcher, not adviser. This distinction keeps us on the right side of financial regulations. The UI and prompts reinforce that any results are hypothetical and not to be construed as advice.
By implementing these safety measures, we ensure the agent remains a value-add and not a liability. This not only prevents catastrophes but also builds trust with users/judges – they see that every possible angle for misuse or error has been considered (from both an AI perspective and a security perspective). Our system as described aligns with the NIST AI Risk Management Framework’s core functions: map out risks, measure and monitor (Sentry), manage through controls (sandboxing, oversight)[2]. It also addresses multiple items in OWASP’s Top 10 for LLMs (LLM01 Prompt Injection, LLM03 Training Data Poisoning, LLM05 Supply Chain, etc.)[3]. This thorough approach to agent safety differentiates SignalOps from typical “AI agent hacking something together” projects – we treat the AI as a supervised junior analyst whose work must be checked and controlled.

Financial Compliance and Non-Advisory Boundary
Because SignalOps deals with stock market analysis, we must be careful to not cross into the realm of providing investment advice or any service that could trigger regulatory oversight (like being deemed an investment advisor). We design both the user experience and the underlying functionality to stay on the “research/education” side of the line.
Clear User Communication: The UI will conspicuously label outputs as “Paper Trading Research”, “Hypothetical Results”, and “Not Investment Advice”. Instead, factual: “Strategy X had a 10% annualized return in simulation with Y volatility. Further analysis is required for real-world viability.”
No Personalized Recommendations: We are not taking in any user’s personal financial data or risk preferences to output a tailored strategy. That would tread into advice territory. Instead, our agent just researches generic strategies. This keeps it more like a tool or a platform, not an advisory service. The SEC has guidance for robo-advisors which emphasizes disclosures and clarity if it were advice【57†】, but we choose not to be an advisor at all.
Paper Trading Enforcement: We integrate with a brokerage API (if at all for paper execution) strictly in paper trading mode. For instance, Alpaca provides a separate base URL and API keys for paper trading accounts[26][25]. Our system will be coded to only accept paper trading API keys or endpoints. If someone tried to plug in a live trading key, we either prevent it or strongly warn and require extra confirmation. In a hackathon context, we might not even reach the stage of sending orders to a paper broker (we can simulate the whole pipeline), but if we do, it’s segmented behind a feature flag.
Regulatory Considerations: - We are aware of FINRA’s guidance on digital investment advice tools[28] and the need to supervise algorithms and maintain records. Although we are not giving advice, we voluntarily adopt a record-keeping posture (we log everything the agent does and keep reports – which is akin to how a firm would retain research reports and model changes). - If this were to be more than a hackathon project, we’d consider if it falls under any definition of an investment advisor (likely not as long as we don’t advise actual trades to others, but if we did, registration or an exemption would be needed). - We ensure that any user-facing descriptions don’t promise profits or make guarantees. This is partly ethical and partly to avoid any misinterpretation that could draw regulatory ire.
Privacy: There isn’t much personal data here, but if we use any user account (like GitHub for login, or their Alpaca keys), we handle it carefully (store encrypted if stored at all). This aligns with regulations like GDPR if we had EU users, etc. But likely not a big issue here.
Overall Stance: We present SignalOps as a “sandbox for strategy research” not a trading platform. Even the name “SignalOps” implies operations on signals, not a robo-advisor or auto-trader. By keeping that framing, we stay clear of being a service that tells an investor what to do. In the final demo, we might explicitly mention, “Note: This system is for demonstrating research automation. It does not directly interface with live trading and remains an internal tool.”
This conscious boundary not only keeps us safe legally, it also reinforces the safety ethos of the project. We prefer to have a cautious, well-evaluated strategy rather than a rushed deployment. If one day a strategy graduates from research to a real fund, it would go through an entirely separate approval process outside this system’s scope.

End-to-End Workflow Summary (SignalOps in Action)
Bringing it all together, let’s walk through how a complete cycle works in practice, from the agent’s idea to a vetted strategy update:
Agent Proposes an Experiment: Based on previous results or a prompt from the user (“try something new”), the AI agent formulates a hypothesis. For instance, it might say: “Strategy Alpha has high volatility. I will attempt to add a volatility filter to reduce drawdowns (e.g., go to cash when VIX > 30).” This proposal is generated by the LLM agent using its internal prompt (which contains recent performance info and any user guidance). The agent writes the code changes (maybe modifying the strategy code to incorporate the VIX filter) and updates config files accordingly. It then prepares a description of the experiment.
Experiment Initialization (PR Creation): The agent through the orchestrator creates a new Git branch (e.g., exp-vol-filter) and commits the changes (code + perhaps a config YAML noting the experiment settings). The orchestrator then opens a Pull Request on GitHub with title like “Experiment: Add Volatility Filter to Strategy Alpha”. The PR description is populated with the agent’s explanation and links (the PR might include a placeholder for results that will be updated later, or we open it after results – we have a choice to PR before or after running backtest. We could do before to get CodeRabbit started in parallel, or after to include results. We may do after so that we attach report artifacts to the PR.)
Daytona Run Execution: The orchestrator now creates a Daytona sandbox to actually run the backtest for the experiment. (If we PR’d first, we ensure the sandbox pulls the PR’s branch.) It attaches necessary data volumes and executes the pipeline. The log stream from Daytona is forwarded live to the UI – the user can watch logs like “Pulling VIX data… Backtesting over 2010-2020… Completed. Sharpe: 0.9” appear in real time[6]. Sentry is tracing this in the background and will catch any errors (if, say, the new code had a bug).
Results Generation: The pipeline finishes, producing metrics and report. The orchestrator collects these outputs from the sandbox. It then signals the UI that the run is complete (perhaps via a WebSocket event or simply the UI polling sees status flipped to done). The HTML report is made accessible (maybe uploaded to an S3 or served directly). The audio briefing is generated here if enabled.
Snapshot & Cleanup: The sandbox is snapshotted for record (ID stored in run manifest) and then stopped to save cost[1]. Now, on Daytona’s side, we have a saved state in case we need to revisit.
Populate PR with Results: The orchestrator (or a CI action) now updates the PR with the results. For instance, it could post a comment to the PR like “Experiment completed. Out-of-sample Sharpe moved from 1.05 to 0.95 (decreased). Max DD from 20% to 15% (improved). See the attached report for full details.” We also attach or link the report and relevant artifacts. If using GitHub Actions, we might have an action triggered after run that uploads the report.pdf as an artifact and comments with a link.
CodeRabbit Review: CodeRabbit’s GitHub App, upon PR creation and new commits, has been doing its analysis. It may now post comments: e.g., “Nit: The code uses global variable for VIX data, consider passing it as parameter.” or “⚠️ The training function is using the full dataset without separation – potential data leak.” These appear on the PR and our UI can fetch them to display next to the results. In our scenario, perhaps CodeRabbit didn’t find a data leak but did notice something like missing unit tests for the new component – minor.
User/Operator Evaluation: The human (developer or analyst) looks at the Dashboard run page. They see the performance drop in Sharpe, read the analysis that while drawdown improved, returns suffered. They also see a warning the agent flagged: maybe the DSR is low, implying not a robust finding. CodeRabbit’s minor comment is noted. The user decides this change isn’t an improvement to adopt permanently. They might give feedback to the agent (maybe as a comment like “This hurt Sharpe too much, try a different approach” or simply by not merging).
Agent Iteration or Completion: If the experiment was unsuccessful, the agent uses the feedback (performance metrics, etc.) to propose a different experiment next time. If it was successful (say Sharpe improved without other issues), the humans might choose to merge the PR – thus updating the main strategy. That strategy could then be scheduled for periodic re-evaluation (which our Cron integration with Sentry would monitor). The system then goes back to monitoring until a new idea emerges.
Incident Handling: Suppose the experiment triggered an alert – e.g., Sentry noticed a sharp drop in performance or an error in the run. That would show up on our UI (maybe an “Incidents” badge). The team can click it and see what happened (with Sentry’s details). For example, “Alert: Strategy Alpha Sharpe fell below threshold in latest run.” This might cause the agent to step back and analyze why, or the humans to direct a rollback of recent changes.
Throughout this process, every action was logged, every outcome recorded. We have: - A Git history of changes. - A Sentry trace of the run. - A report artifact of results. - A CodeRabbit review of code quality. - A Daytona snapshot of environment. - An audit trail of sandbox actions. - Human oversight at crucial points.
This end-to-end flow demonstrates how SignalOps is not a black-box auto-trader, but an intelligent research assistant operating under strict governance. It’s akin to an intern analyst who does lots of calculations and even writes draft code/reports, but always checks in with the portfolio manager (the human) for approval.
For the hackathon demo, we can walk the judges through this flow in an accelerated fashion: - Show the dashboard, trigger a run (or have one recently run to inspect). - Watch some live logs (maybe highlight Daytona’s speed by showing how quickly environment spins up). - Show the results and how the PR and CodeRabbit comments look. - Emphasize how easy it is to follow what happened due to links to everything (transparency). - Possibly show the audio summary for flair. - Show how one could re-run the same experiment from snapshot to verify it (if time permits).
This narrative solidifies that our project isn’t just a bunch of disjointed tools – it’s a cohesive pipeline where each sponsor’s technology enhances a specific aspect: Daytona for execution, Sentry for monitoring, CodeRabbit for review, ElevenLabs for presentation, and the agent tying it all together.

“EarningsCall Lens” Feature Integration
As an alternative application of SignalOps’s capabilities, we introduce EarningsCall Lens – a mode where the system analyzes corporate earnings call transcripts and correlates them with stock movements, rather than focusing on technical trading signals. This showcases the flexibility of our platform (and another creative use of AI in finance).
Use Case: Many traders want to gauge if what executives say in earnings calls (and how they say it) can predict short-term volatility or direction in stock price. The EarningsCall Lens automates the process of fetching an earnings call (or using a provided transcript), analyzing its sentiment/tone, and then seeing if there was any significant market reaction.
Data Requirements: We need transcripts of earnings calls (or at least the prepared remarks and Q&A). Potential sources: - Some companies post transcripts publicly. For demo, we can use a few known transcripts (maybe manually obtained beforehand). - There are APIs like Finnhub, Alpha Vantage, Polygon that provide transcripts. Finnhub has an earnings call transcripts endpoint (but requires API key, limited usage). Since user wants minimal paid API, we might use Financial Modeling Prep (FMP) which has some free transcript data or scrape a site like SeekingAlpha for one example (careful with terms). - Alternatively, use an example from a prior quarter which we hardcode or include in dataset to avoid live API calls.
Integration in Daytona: We treat the transcript text as just another dataset. Possibly stored as a text file or in a small database. When the agent or user selects a company and date, if we don’t have it, we fetch it (Daytona can do that or external script) and cache it.
NLP Analysis: The agent (or a specialized part of pipeline) will: - Summarize the key points of the call (could use an LLM prompt to summarize, but that might be expensive or we can use an open model since summarizing one doc is feasible). - Perform sentiment analysis or even an “uncertainty/optimism” scoring. There’s research on measuring sentiment in earnings calls (e.g., count of positive vs negative words, or more advanced embeddings). - Detect any specific guidance or noteworthy statements (maybe using keyword search or another model prompt focusing on risk factors mentioned). - Possibly classify the call’s tone as bullish, neutral, or bearish.
Correlation with Market Reaction: We then look at the stock’s price around the call date: - Calculate the 1-day, 1-week post-call return, and the volatility. - Check if there was an unusual move (like stock jumped 10% next day, implying the call had surprising news). - Compare to the sentiment: e.g., call was very positive but stock fell – that’s interesting (maybe market expected even more).
Output (EarningsCall Report): For this lens, we produce a report focusing on: - A summary of the call content (key takeaways). - The measured sentiment score or indicator (maybe on a scale or just highlight words). - A chart of stock price before and after the call (say 5 days before to 5 days after) to visualize the reaction. - A brief analysis: “The CEO’s tone was optimistic, mentioning improved revenues and expansion. The stock, however, dropped 5% the next day, possibly due to guidance that fell short of expectations. Volatility was elevated (daily vol doubled) post-call.” - If multiple transcripts are analyzed over time, we could find patterns (like does this CEO’s sentiment correlate with subsequent moves consistently? This might be too deep for now, but it’s an idea).
Agent Involvement: We could have the agent handle this analysis via tools as well: - A tool to get transcript text by ticker+date. - A tool to get recent price data for that date range. - The agent could then be prompted: “Analyze the transcript and find if the market reaction aligns with the content. Produce a brief commentary.” This would be a different kind of prompt than the strategy one, more of an analyst role. It’s doable and would be an interesting contrast (LLM used for natural language analysis vs coding). - The agent might not need to code here, just read and summarize, which is simpler.
Integration into UI: - Provide a search/select for a company’s earnings call. - Let user choose from recent calls (we could have a list of a few preloaded for demo). - Once selected, the backend triggers analysis (could also be in Daytona for reproducibility, or done directly via a smaller agent prompt). - Show the results on a dedicated page with transcript snippets, summary, and price chart. - Possibly allow the audio of key parts of call (if we had the actual audio and ElevenLabs could clone voice – probably overkill and legally tricky). More feasible: use ElevenLabs to narrate our summary in a “news reporter” style voice.
Reproducibility: If we incorporate this into the agent loop, we ensure transcripts are saved and versioned. We might snapshot the analysis sandbox as well, though it’s less about code and more about data. Still, an output report can be generated for this analysis as well.
Benefit: This feature broadens the appeal of our project beyond pure quant trading signals. It shows we can apply the same infrastructure to fundamental/NLP-based analysis. It might interest judges who think about use cases for LLMs in finance.
From an integration standpoint, it uses the same components: - Daytona (to fetch data and run analysis in isolation). - Possibly Sentry (if we schedule such analyses regularly for new earnings). - ElevenLabs (could narrate a quick “Company X’s call was bullish, but stock fell…” audio). - CodeRabbit is less relevant here because there’s not much code being changed, but we might still keep any code in PR if agent writes a new analysis script or so.
We will implement EarningsCall Lens as an optional path – it doesn’t interfere with the main trading strategy loop, it’s triggered separately. In the architecture, it could be a separate command to the agent (“analyze earnings for AAPL Q3 2025”) vs (“improve strategy Alpha”).
If time allows during hackathon, we’d demo both modes to show versatility. If not, we at least mention it in documentation to show extra creativity even if not fully built out.

Set up one alert in Sentry: e.g., a metric alert (this might be done in Sentry UI rather than code, we’ll mention it in docs).
Also make sure any exceptions bubble to Sentry (so if our orchestrator crashes, we know).
AI Agent Integration: This is one of the last pieces – making the agent generate experiment ideas and code changes. Given time constraints, this could be simplified:
We might use a prompt and the OpenAI API to have it output a patch or code suggestion. But doing full autonomous coding reliably is hard in short time.
Alternatively, have a set of pre-defined experiment scenarios and code diffs that the agent would have done, and cycle through them (so the flow appears agent-driven but is partly scripted).
If we do attempt the real agent, we can run a local MCP client (like using Daytona’s MCP which supports connecting GPT-4)[30]. That’s advanced; likely we mock this.
For presentation, it might be enough to describe the agent’s logic or have a simple rule-based “agent” (not LLM) that picks the next experiment based on a pattern (like toggling a parameter).
Given the question says “it includes training an ML model” – if we interpret that as the agent might try an ML-based strategy, we ensure our pipeline can handle that (like a flag to train a simple classifier vs a fixed rule).
ElevenLabs TTS:
Add a utility to call ElevenLabs API with a given text. Test it with our API key on a short string.
In orchestrator after report generation, craft summary text. We could either generate this summary via a template + numbers or even ask the LLM to generate a concise summary.
Feed to ElevenLabs, get MP3, save to a known path (and maybe upload to a cloud storage or serve directly).
UI should have an audio element pointing to that MP3 URL.
Confirm audio plays in browser.
EarningsCall Lens:
Prepare one or two sample transcripts (e.g., Apple Q1 2023, Tesla Q4 2022).
Write a script to do sentiment analysis. Perhaps use a simple approach first: a word list of positive/negative words count, and perhaps an LLM call to summarize.
Create a small page or modal in UI to trigger this analysis. The agent involvement can be minimal, maybe just run a predetermined analysis code on selection.
Ensure it produces a report or at least some output to display (chart of stock move: can use a chart library or just an image pre-generated).
This feature could be partially implemented if short on time, but at least outline it in code/comments.
Final Polishing:
Add all the disclaimers and safety warnings in UI (e.g., a modal or page detailing the non-advice policy and known simulation limits, possibly must be accepted by user).
Test an end-to-end run with all pieces: Starting run -> logs -> results -> PR -> CodeRabbit -> Sentry -> audio.
Fix any issues, improve error messages (so if something fails, user sees a friendly note rather than nothing).
Prepare some seeded runs so that even if something goes wrong live, we have data to show (like have some completed runs in the DB to browse).
Write documentation (maybe a Notion page or extend README) to guide through using the app.
Each of these tasks can be worked on independently to an extent. Using the Appendix A tasks as reference: - (1) corresponds to step 1 above (repo scaffolding). - (2) Daytona integration corresponds to steps 2 and partially 4. - (3) Pipeline corresponds to step 3 (and ongoing improvements). - (4) Reporting corresponds to step 5 (report gen in pipeline and UI display). - (5) Observability corresponds to step 7. - (6) PR flow corresponds to step 6 (and a bit of 8). - (7) ElevenLabs corresponds to step 9.
By following this plan, we incrementally build up the system, verifying at each stage. The end result will be a sophisticated system that, despite the tight schedule, appears seamless and fully featured to users. The key is focusing on integration and having something to show for each component – which we’ve prioritized in this breakdown. The use of sponsors’ tech (Daytona, Sentry, etc.) is woven throughout the steps, ensuring we don’t leave integration to the last minute (since showcasing those is critical).

In conclusion, SignalOps will be implemented as a comprehensive platform where an AI agent, constrained by robust guardrails, can autonomously conduct stock market signal research. We leveraged every sponsor’s capabilities: Daytona for environment reproducibility and safe execution[1], Sentry for intelligent monitoring of strategy performance, CodeRabbit for AI-assisted code reviews, and ElevenLabs for transforming analytical results into engaging audio updates[8]. With careful attention to security, compliance, and best practices, our plan ensures that SignalOps is not only feature-rich and innovative but also trustworthy and maintainable – qualities that fulfill the hackathon’s judging criteria and make for a compelling demonstration.
